Architecture

The package reads a city's data (site.toml, events/, venues.json) and writes a static site: self-contained HTML pages (inline CSS and JS), feeds and embeds. Julia string interpolation builds the markup; there are no templates.

Data flow

events/**/*.json ─ load_events ─▶ Vector of JSON.Object ─▶ renderers ─▶ write_site ─▶ _site/
issue body ─ parse_issue_form ─▶ events_from_form / _table / _json / apply_correction ─▶ event files
events/**/*.json ─ read_event ─▶ Event (struct) ─ set_path ─▶ write_event   (bulk edits)

Events are plain dictionaries (JSON.Object, which keeps the key order) everywhere except the bulk edit, which uses the typed Event struct.

Context in scoped values

Three ScopedValues carry the context, so helpers need no extra arguments:

ValueSet byHolds
SITEmain, write_site (_with_site)The TangoKalender.SiteConfig: name, city, URLs, map, texts.
LANGeach public renderer's lang= (_with_lang)"nb", "en" or "es".
VENUESwrite_site(…; venues=), the CLIThe geocoding cache, so builds never use the network.

Nothing site-specific is hard-coded: use site_url(), repo_url(), site_name(), site_city() and the form-URL functions. A test fails on a hard-coded site URL.

The site

  • Views (src/render/html.jl): index.html (compact list), uke.html (week), kart.html (map), kort.html (cards). They hold only events that haven't ended by the build date (the week view keeps the whole current week), so pages stay small and show no old events, also without JavaScript. One page script filters the rows (and still hides events that end between nightly builds); the filter state lives in the URL.
  • Archive (render_archive_html): past events, one page per year (tidligere-YYYY.html, newest day first, with search and type/music filters); tidligere.html is the newest year. Old ?when=all links are sent there.
  • Event pages (src/render/event.jl): arrangement/<id>/ with JSON-LD, link previews and a map.
  • Feeds and embeds: kalender.ics and per-event .ics (src/ics.jl), rss.xml, events.json, the SVG images that pick the current day themselves (src/render/svg.jl), and an iframe list (src/render/embed.jl).
  • Languages (src/i18n.jl): Norwegian at /, English at /en/, Spanish at /es/, with the same file names. Every UI string is in _T in all three languages; a test fails on a missing one.
  • Submission pages (src/render/submit.jl, src/llms.jl): «Legg til», the AI prompt and llms.txt.

Intake

The issue forms' labels are the parser's keys, so the canonical forms live in templates/ISSUE_TEMPLATE/ and data repositories get rendered copies. parse_issue_form splits a form; the plain form, the spreadsheet (events_from_table) and the JSON route (events_from_json) all end in the same event rules, and corrections go through apply_correction. Times are always recomputed as Norwegian local time.

Bulk edits and trimming

src/eventstruct.jl, src/edit.jl, src/repeat.jl and src/render/term.jl implement tangokalender edit and repeat on the Event struct. That code is written so juliac --trim can compile it into the stand-alone tangoedit:

  • keys reach fields through generated if chains instead of lenses built from strings;
  • field types are passed as Val, and nested keys use one function per level instead of recursion;
  • dates are parsed by hand;
  • terminal output goes through TangoKalender.ansi_text instead of StyledStrings.

Keep it that way and run bin/build_tangoedit.sh after changing that path.

The event form and TangoTUI (experimental)

src/eventform.jl is the form behind interactive editors, independent of any terminal library:

  • form_fields() lists the fields in order, with Norwegian labels and help and the allowed values of choice fields;
  • field_text and set_field read and write a field as the text an editor types, through set_path (dates, times with the Oslo offset, the end after midnight, video links, the other language);
  • field_problems maps check messages to fields;
  • event_search_text and search_matches are the list search;
  • changed_fields, later_in_series, later_in_selection, split_by_organizer (the guardrail: only the same organiser) and copy_fields apply one change to later dates;
  • save_form_event writes one or several events at once, all or nothing.

TangoTUI/ is a separate package (its own Project.toml, TangoKalender by path, plus Tachikoma.jl) with the full-screen editor on that form. Tachikoma pulls in REPL and Pkg and can't be trimmed, so it stays out of TangoKalender's dependencies and out of tangoedit. Its tests drive the editor with key events and read the screen from Tachikoma's TestBackend; bin/make_tui_demo.jl uses the same screens for the animated demo (Tachikoma's export_svg). A trimmed interactive mode for tangoedit would reuse eventform.jl with a small terminal layer of its own (an earlier trim spike is on the experimental/interactive-tangoedit branch).
