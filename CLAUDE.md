# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A small Julia package that turns a city's tango events (one JSON file per event under `events/` in that city's **data repo**, e.g. Oslo: `Tangokalender/tangokalender.github.io`) into a static site of self-contained HTML pages (inline CSS and JS; the only external assets are Leaflet from cdnjs and OpenStreetMap tiles, on map pages). Visitors can search, filter and sort events. The site is in three languages (see `src/i18n.jl` below): Norwegian Bokmål at `/` (primary), English (UK spelling) at `/en/` and Spanish (rioplatense voseo) at `/es/`. **Every new UI string goes into `_T` with all three languages**; a test fails on a missing one. Data values stay English slugs (schema enums such as `milonga`, `outdoor`); `src/labels.jl` maps them to Norwegian display labels through `_TYPES` and `_MUSIC` (also used by the Norwegian issue-form parser), and `_TYPES_I18N`/`_MUSIC_I18N` in `src/i18n.jl` hold English and Spanish. Add any new enum value to all of them.

## Commands

```bash
# Install dependencies and run the tests
julia --project=. -e 'using Pkg; Pkg.instantiate(); Pkg.test()'

# CLI entry point (TangoKalender.main): build is the default subcommand; paths are relative to the cwd
julia --project=. -m TangoKalender validate [events]                   # exit 1 on problems
julia --project=. -m TangoKalender [build] [events] [public/index.html] [--title=… --subtitle=… --no-validate]
julia --project=. -m TangoKalender site [events] [_site]   # whole site: index.html, uke.html, kart.html, kort.html, tidligere(-YYYY).html, legg-til.html (+ for-ki.html redirect), arrangement/, kalender.ics, rss.xml, llms.txt, mal/, schema/*.json (used by pages.yml)
julia --project=. -m TangoKalender from-issue BODY.md [--root=events] [--issue-url=URL] [--report=r.md] [--today=YYYY-MM-DD]
julia --project=. -m TangoKalender templates [DIR]        # render templates/ISSUE_TEMPLATE for the site into DIR/.github/ISSUE_TEMPLATE
julia --project=. -m TangoKalender init-site DIR --slug=bergen --city=Bergen --site-url=… --repo-url=…   # new city data repo
julia --project=. -m TangoKalender edit TERM… [KEY=VALUE…] [--preview|--json|--dry-run] [--from=… --until=… --all --root=events]
                                           # bulk edit; without KEY=VALUE it only lists the matches (edit --help)
julia --project=. -m TangoKalender repeat TERM… --every=2weeks|month [--on=last-friday] [--count=N|--until=DATE] [--except=…] [KEY=VALUE…]
julia --project=. -m TangoKalender repeat TERM… --on=2026-12-27[,DATE…] [KEY=VALUE…]   # given dates, any weekday
                                           # copy an event to new dates (repeat --help); also `tangoedit repeat`

# Trimmed stand-alone `tangoedit` (= edit, ~0.03 s startup, needs network the first time for JuliaC)
bin/build_tangoedit.sh && build/tangoedit/bin/tangoedit esa-tandas --root=events

# Install as the `tangokalender` app (Pkg apps, Julia ≥ 1.12). Apps.add(path=) needs a git repo; use develop locally
julia -e 'using Pkg; Pkg.Apps.develop(path=".")'
```

`src/precompile.jl` is a PrecompileTools workload that runs the CLI commands (from-issue, validate, edit, site, build; not geocode) on a temporary tree, so a CLI run takes about 2 s instead of about 30 s, at the cost of about 1.5 min more precompilation. When you add a command or a code path that is slow on first use, add it there. The trimmed `tangoedit` starts in about 0.03 s.

`bin/build_site.jl` and `bin/validate_events.jl` are thin wrappers around `TangoKalender.main`. `bin/make_og_image.jl [out.png] [--site=site.toml]` draws a site's link-preview image (city and address from `site.toml`; without one, the package's generic `assets/og-image-generic.png`).

`test/runtests.jl` runs `test/tests.jl` (plain `@testset`s, no TestItems) as the Oslo **test site** `test/fixtures/site/` (`site.toml` plus a frozen copy of the Oslo `events/` and `venues.json` from 2026-10-10), so the tests never depend on the live data; `TREE` and `FIXTURE_SITE` point there. `test/fixtures/media/` is a small valid tree that exercises flyer, video and music style. The `julia` MCP server is set up in `/workspace/.mcp.json`. Prefer a persistent session (`julia_create_session` + `julia_eval_code`, with Revise) over repeated `julia` invocations, which recompile every time. `/workspace/dev-oslotango/` is a dev environment that `[sources]`-links this package by path.

## Architecture

- `src/TangoKalender.jl`: the module. It `include`s the files below and exports the public API.
- `src/site.jl`: **one site per city**, configured by `site.toml` at the root of the data (schema `schema/site.schema.json`): `slug`, `name`, `city`, `site_url` (may include a path, e.g. `…/bergen`), `repo_url` (the data repo with the issue forms), `og_image`, `[map] center/zoom`, `[geocode] countrycodes/viewbox` and `[texts.nb|en|es]` (overrides `_T` keys). `SiteConfig` is carried in the ScopedValue `SITE` (like `LANG`/`VENUES`): `main` wraps every command in `_with_site` (`--site=FILE`, else `./site.toml`, else the current site; outside any scope `DEFAULT_SITE`, a placeholder «Eksempelby»), and `write_site(…; site=)` likewise. **Nothing site-specific is hard-coded**: use `site_url()`, `repo_url()`, `site_name()`, `site_city()`, `site_host()` (ICS UIDs), `submit_form_url()`, `correct_form_url()`, `table_form_url()`, `json_form_url()`, `og_image_url()`, `llms_url()`, `submission_schema_url()`. `_t` fills `{city}`/`{CITY}`; the about, embed and AI texts interpolate `site_city()`. `_addrkey` strips the site's city, so load venues inside the site scope. `write_site` rewrites the schemas' `$id` to the site (`_site_schema`). Norway only: one time zone (`oslo_offset`, `Europe/Oslo`), NOK, Norwegian forms. The tests run as the Oslo site (`test/runtests.jl` wraps `test/tests.jl`); the testset «site config» builds a second city under a path and checks that nothing from Oslo leaks.
- `src/i18n.jl`: languages.
  - The current language is a `ScopedValue` (`LANG`, read with `_lang()`). Public renderers take `lang=` and wrap a private `_render…` in `_with_lang`, so helpers need no language argument. Outside a renderer it is `"nb"` – bot messages, PR titles and `correction_url` (the GitHub forms are Norwegian) rely on that.
  - `_t(key, args…)` returns a string from `_T` (`{1}` placeholders); `_strings!` adds keys (also from other files). Long prose pages keep per-language blocks in functions: `_about()` (about.jl), `_add_text()`/`_COLUMN_HELP`/`_GLOSSARY` (submit.jl), `_embed_text()` (embed.jl).
  - Dates: `_day`, `_longday`, `_dm`, `_wd3`, `_range`, `_weeklabel` (nb «fredag 9. okt», en «Friday 9 Oct», es «viernes 9 oct»).
  - URLs: each language tree has the same file names; `_prefix(l)` is `""`, `"en/"` or `"es/"` and `_lang_url(rel)` the absolute URL. `_alternates(rel)` writes canonical + hreflang (x-default = nb). `_langnav(rel; depth)` is the NO · EN · ES switcher with **relative** links and SVG flags (`_FLAGS`, part of `_SPRITE`, so every page with a switcher includes `_SPRITE`). Flags are SVG, not emoji, because Windows shows flag emoji as letters.
  - `_lang_js(rel; depth)` is the head script on every site page: clicking a language link stores `localStorage.lang` and carries `?filters#hash` along; **Norwegian pages only** redirect a visitor without a stored choice by `navigator.languages` (nb/nn/no/da/sv → stay, en, es, anything else → en). `/en/` and `/es/` are never redirected, nor bots and headless browsers (`HeadlessChrome` – so the browser tests are not redirected). Tested by `test/js/lang.js` (Node ≥ 21 has its own `navigator`; the harness redefines it).
  - Event text: `title`/`description` are in the event's `lang` (default nb), `translations` holds others. `_text(e,"title")` picks page language → (es: en) → original → any, and returns the language; `_langattr`/`_langnote` add `lang="…"` and «(på engelsk)» when it differs. `data-search` holds all versions (`_alltext`).
- `src/geo.jl`: map positions. `venues.json` (repo root, schema `schema/venues.schema.json`) caches address → `{lat, lon, precision, source}`, keyed by `_addrkey` (lower case, no postcode, no «Oslo»).
  - `geocode!`/`tangokalender geocode` query Nominatim **only for addresses not in the cache**: 1 request per second, identifying User-Agent. When Nominatim finds nothing or only the street, `_kartverket` asks Kartverket's address register (ws.geonorge.no, Norway only: `countrycodes` must include `no`): `_kv_query` puts street + city in `sok` with abbreviations as wildcards («Chr.» → «Chr*», which neither service matches otherwise), and only an exact house number/letter match is accepted (the postcode picks between several; still ambiguous → nothing); stored as `source: "kartverket"`, `precision: "house"`, with the matched address in `note`. Not-found stored as `precision: "none"` (retried only with `--retry`), network errors not stored. `source: "manual"` entries are hand-edited and never touched. The intake workflow runs `geocode` and commits `venues.json` with the bot PR.
  - `venue_coords(e)` returns a position **only for `precision: "house"` or manual entries** – the «precise enough for a map» rule.
  - **Builds never use the network.** The cache is in a `ScopedValue` (`VENUES`): `write_site(…; venues=load_venues())` and the CLI (`--venues=`, default `venues.json`) set it; without it, no maps.
- `src/render/map.jl`: Leaflet (pinned version with SRI hashes, `LEAFLET_HEAD`) and OSM tiles, loaded automatically, only on map pages.
  - Event pages get a map card (`_event_map`) and JSON-LD `geo`.
  - The «Kart» view (`kart.html`, `view="map"`) is the compact list plus a map. Rows carry `data-lat`/`data-lon`/`data-venue`/`data-dl` (from `_data_attrs`), and `_MAP_JS` is appended to the page script. `_JS` calls `window.onfiltered(visibleRows)` after every filter change, and `mapMarkers` groups them into one marker per venue (`window.__markers` holds the data even without Leaflet, which is what the tests check).
  - The time filter's default comes from `data-default` on `#when` (`week` on the map, `upcoming` elsewhere), so URLs, «Nullstill» and the filter count treat each view's default as «no filter».
- `src/models.jl`: events are plain dicts (`JSON.Object` when parsed, which keeps key order) everywhere except the bulk edit (below). `load_events(path)` reads a directory tree via `load_event_tree` or a single JSON file holding an array of events. `event_path` gives each event's canonical file location (and throws if there is no `start`), and `save_event_tree` writes to it. `expand_weekly` turns a weekly template (`weekday`/`start_time`/`end_time`, which exist only in the template, never in stored events) into dated events with ids `<series>-YYYY-MM-DD`. It uses `oslo_offset` for the summer/winter time offset (no TimeZones dependency), and the issue forms use it for «Gjentas: Ukentlig».
- `src/eventstruct.jl`: `Event` (+ `Venue`, `Video`, `Translations`/`Translation`), a typed view of one event file with StructUtils `@kwarg`. **Its fields must match `schema/tango-event.schema.json` in order** (a test checks this; add new schema fields here too). `$schema`/`end` are the fields `schema`/`end_` (`_jsonname`). `read_event` returns the struct plus the file's key order, and `write_event` writes it back in that order, leaving out keys that were absent and are still null: an unchanged event is byte-identical (tested on all of `events/`). `set_path(e, ["venue","name"], raw)` converts `raw` (JSON, else plain text) to the field type and sets it with `Accessors.set` + `PropertyLens`. `check(::Event)` repeats the schema rules on the struct.
  - **Written for `juliac --trim`**: keys reach fields through `@generated` `if` chains (`_withfield`, `_setfield`), field types are passed as `Val`, nesting uses one function per level (`_set1/2/3`) rather than recursion, dates are parsed by hand (`_ymd`, `_parse_dt`, `_two`, `_pad`: Dates' format strings, `lpad`/`rpad` and `relpath` don't trim), and function arguments are type parameters (`where {C}`) so they get specialised. Keep it that way and rebuild with `bin/build_tangoedit.sh` after changes on the edit path.
- `src/edit.jl`: `tangokalender edit` (`edit_main`). `find_events(terms)`: all terms must match (plain text in `SEARCH_KEYS`, or `key:text`, aliases `type:`, `teacher:`, `music:`, `org:`); upcoming only unless `from=nothing`. `edit_events(terms, edits)` applies `KEY=VALUE`s, runs `check` on each event, writes through `_write_files!` (shared with corrections in `models.jl`: refuses to overwrite, moves files on a new date/id, rolls back if `tree_check(root)` finds problems). `check_event_tree` is the struct-based `validate_event_tree` for the trimmed build.
- `src/repeat.jl`: `tangokalender repeat` / `tangoedit repeat` (`repeat_main`, reached from `edit_main` and `main`). `repeat_events` copies a template event (`repeat_template`: one match, or the latest of one series; `template_note` warns, as `note` in the result and on stderr, when that latest one has another weekday or title than most of the series and names a typical id to copy) to the dates of a `Recurrence` (`recurrence_dates`: every N weeks/months, same day of month or `--on=2nd-thursday`/`last-friday`, `--count`/`--until` (default today + 6 months), `--except` dates/ranges that don't count), or to given dates (`--on=YYYY-MM-DD,…`, `repeat_events(terms, dates)`; `_repeat_events` takes them as `ondates`). Copies get id `<series>-YYYY-MM-DD`, times with the offset recomputed (`_move_stamp`, `_oslo_offset`), status scheduled, `first_seen` today. Dates with the same id/file, or with any event of the series that day, are skipped (`exists`). Writes through `_write_files!` with `old=nothing` (new file). Trim-safe like edit.jl. `repeat_from(t, keys; rule|dates, …)` is the same for a template you already have (an editor's form, saved or not; `start` defaults to the day after it), over the positional core `_repeat_from` that `_repeat_events` calls after finding the template; its result adds `unused_except`. `_template_oddity(t, group)` is the holiday-special check behind `template_note`, for front ends to word their own note.
- `src/eventform.jl`: the event form shared by interactive editors. `form_fields()` lists the fields in order (Norwegian labels and help, `kind`, allowed `choices` from `TYPE_ORDER`/`_TYPES`/`_MUSIC`, and the `check` keys that belong to each), `field_text`/`field_values` read a field, `set_field` writes it through `set_path` (form-only keys: `date` moves start and end like `repeat_event`, `start_time`, `end` = «TT:MM» overnight or a date, `video` from a URL, `other_title`/`other_description` in the language that isn't `lang`, empty translations pruned) and throws `ArgumentError` with a Norwegian message for unreadable text; `field_problems` maps `check` messages to fields. `new_event`, `form_id` (`<series or slug>-YYYY-MM-DD`) and `save_form_event` (sets `last_verified`, writes through `_write_files!`) cover saving. Changing several events: `changed_fields` (never the date), `later_in_series` (same series from this date on, like «Rett opp»'s «Denne og alle senere datoer»), `later_in_selection` (an editor's search result from this date on), `split_by_organizer` (the **guardrail**: only events with the edited event's organiser, ignoring case/spacing, may change; the rest are reported as skipped), `copy_fields` (through `set_field`, so times are recomputed per date and a multi-day end keeps its length) and `save_form_event(…; others)`, which writes all files in one `_write_files!` (all or nothing). `event_search_text`/`search_matches` are the editors' list search: like the web page's `data-search` (title in all languages, venue, organiser, DJ, description, «avlyst») plus teachers, types, id, series, date and weekday; every word must match, `key:text` words go through `SearchTerm`/`matches` as in `tangoedit`.
- `TangoTUI/` (**experimental**, Julia only; docs page `docs/src/editors/tangotui.md`, demos `bin/make_tui_demo.jl` and `bin/make_tui_repeat_demo.jl`, rerun both after changing how TangoTUI looks): a separate package (its own `Project.toml`; TangoKalender by path, plus Tachikoma.jl) with a full-screen editor on that form. It starts on a searchable list of the upcoming events (`:search` mode: type to filter, ↑/↓ + Enter opens, Ctrl-A past events, Ctrl-N new, Ctrl-K copy, Ctrl-R repeat; Esc in the form returns to the list, reloaded; saving a change asks whether it also applies to later dates of the series (a) or of the search (u), within the organiser guardrail): `julia --project=TangoTUI -m TangoTUI [--all] | [edit] TERM… | new [TERM…] | repeat TERM…`. The repeat panel (`:repeat`, `RepeatForm` in `m.rep`; Ctrl-R in the list or the form, where the form's current event is the template) has Norwegian fields for every `repeat` option (`_RFIELDS`, pick lists `_RULES`/`_NTH`/`_UKEDAGER`, inapplicable fields dimmed and skipped) and redoes a dry run of `TK.repeat_from` after each change, listing new and skipped dates on the right; Ctrl-S writes them. Ctrl-L in a saved event (`:spread`, `_spread!`/`_view_spread`) copies its values to the later dates of its series after a correction made for one date only: `TK.series_differences(e, later)` lists the fields that differ (never the date) with the count and the one value they share, if any; fields are pre-ticked when all later dates share one value, never Status; writing goes through `_write!` (organiser guardrail, `copy_fields`, all or nothing). `:longtext` fields (the two descriptions) open in a modal (`:long`, `WrapEditor` in `m.long`, drawn by `_view_long`) with word wrap (`_wrap_lines`: words move whole, overlong words are cut, `\n` stays a line break; Enter inserts one, Ctrl-S applies through `_apply!`, Esc cancels). `TangoTUI/src/precompile.jl` is a PrecompileTools workload (time to the first screen 7.4 s → 2.3 s in a pty that doesn't answer Tachikoma's terminal queries, which wait up to ~1.2 s): it runs the real `Tachikoma.app` headlessly (`io=IOBuffer()`, `tty_size`, `input=IOBuffer(keys)`; Ctrl-C, not a lone Esc, closes panel/form/list) on an invented tree in a temp dir with a `site.toml`, under a watchdog that sets `m.quit`, and drives the other modes through `update!`/`view`. Add new modes there. Julia only: Tachikoma doesn't trim (REPL/Pkg via its deps), so it is not in TangoKalender's deps and not in `tangoedit`. Its tests (`TangoTUI/test/runtests.jl`) send `KeyEvent`s and read the screen from Tachikoma's `TestBackend`; `.github/workflows/tangotui.yml` runs them on pull requests and `main`.
- `src/render/term.jl`: the terminal card (`event_card`, like the web `_card`) and list line (`event_line`). Layouts are lines of `(text, face)` segments (`card_lines`, `line_segs`); `styled_text` makes a StyledStrings `AnnotatedString` (faces `TERM_FACES`, registered in `__init__`), `ansi_text` plain ANSI for the trimmed build (StyledStrings' `Any`-typed annotations don't trim). With `before=`, changed parts are highlighted and the old value struck through. `Base.show(::MIME"text/plain", ::Event)` prints the card.
- `app/tangoedit.jl` + `app/Project.toml`: the trimmed executable's entry point: `edit_main` with `render=ansi_text`, `tree_check=check_event_tree`, output buffered and copied to `Core.stdout` (plain `stdout` has no fixed type). `bin/build_tangoedit.sh` builds it into `build/tangoedit/` (~125 MB bundle, 7 MB binary); `.github/workflows/tangoedit.yml` builds and runs it monthly and on demand.
- `src/cli.jl`: `function (@main)(args)` defines `TangoKalender.main`, which returns an exit code (0 ok, 1 validation failed, 2 usage error). It is reached through `julia -m TangoKalender` and the `[apps] tangokalender` entry in `Project.toml`. `main` is deliberately not exported: `using TangoKalender` from a script would otherwise bring `main` into `Main`, and `@main` would run it when the script finishes.
- Input in two languages: the forms, the spreadsheet and the JSON route all take «Tekstspråk» (`lang`: Norsk/English, blank = Norsk) plus optional «Tittel (andre språk)»/«Beskrivelse (andre språk)» (`OTHER_TEXT_FIELDS` → `translations[other]`) and «Tittel (spansk)»/«Beskrivelse (spansk)» (`SPANISH_TEXT_FIELDS` → `translations.es`, whatever «Tekstspråk» is; the JSON route takes `translations.es` directly; the editors' form has `es_title`/`es_description`). Corrections can change them (blank = unchanged, `-` clears); changing «Tekstspråk» relabels the text and moves the nb/en translation with it, leaving `es` alone. Spanish is never the main text language (`lang` is nb/en). LLMs are told never to translate themselves.
- `tangokalender init-site DIR --slug= --city= --site-url= --repo-url=` (`init_site` in `src/scaffold.jl`) starts a city's data repo: `site.toml`, empty `events/` and `venues.json`, a `Project.toml` pinning TangoKalender `v<version>` via `[sources]` over SSH (`CODE_REPO_GIT`; the reusable workflows rewrite `git@github.com:` to HTTPS, since runners have no SSH key), wrapper workflows calling the reusable `site-*.yml@v<version>`, Dependabot, the rendered issue forms, a placeholder `assets/og-image.png`, `.gitignore` and a README with the one-time GitHub setup (Pages, workflow permissions, labels, branch protection).
- `src/scaffold.jl` + `templates/ISSUE_TEMPLATE/*.yml`: the **canonical issue forms** live in the package, because their labels and ids are the parser's keys. `{{site_url}}`/`{{city}}` are filled per site by `render_template`; `tangokalender templates [DIR]` (`write_templates`) writes them to `DIR/.github/ISSUE_TEMPLATE/`. Edit the templates, never the rendered copies, then rerun `templates`.
- `src/issue.jl`: `parse_issue_form` splits a GitHub issue-form body into `### Heading => value`, and `events_from_form` turns that into dated events. Weekly submissions go through `expand_weekly`. It returns `(events, errors)`, with errors in Norwegian that name the form fields. The headings are the `label:`s in `templates/ISSUE_TEMPLATE/nytt-arrangement.yml` and are listed in `FORM_FIELDS`. A test checks that they stay in sync, so rename both together. The type and music options must match the `_TYPES`/`_MUSIC` labels.
- `src/correction.jl`: the «Rett opp» flow.
  - `correction_fields(e)` gives the event's values in form syntax, keyed by the field `id`s in `templates/ISSUE_TEMPLATE/rett-arrangement.yml`. It's used to detect and display changes.
  - `correction_url(e)` prefills **only** `arrangement_id` and the read-only `navaerende` box (`current_summary`). It drops the description if the URL would exceed `MAX_URL`. GitHub resets URL-prefilled fields when the user edits them, so editable fields must never be prefilled.
  - `apply_correction(form, root)` finds the event by «Arrangement-ID», works out which fields changed, and applies them to this date or, with `SERIES_SCOPE`, to all later dates in its `series`. A **blank field means unchanged and `-` clears**, so a lost prefill can never wipe data. Times are recomputed per date, so the clock change stays correct. A date change keeps the `id` and moves the file.
  - `from-issue` treats any form that has «Arrangement-ID» as a correction. It rolls back if validating the tree fails.
  - Avoid GitHub's own query parameters (`title`, `labels`, `type`, …) as field ids; that's why the ID field is `arrangement_id`.
- `src/submission.jl`: JSON submissions, e.g. extracted by an LLM, through `templates/ISSUE_TEMPLATE/nytt-arrangement-json.yml`.
  - `submission_schema()` is **derived** from the stored schema at build time: the `BOT_FIELDS` are removed, `video_url` replaces `video`, and `start`/`end` are relaxed to Oslo local time. It's published at `SUBMISSION_SCHEMA_URL`. Don't hand-edit a copy of it.
  - `events_from_json` strips code fences and prose, renames guessed field names (`FIELD_ALIASES`: `price`→`price_nok`, `flyer`→`flyer_url`, …; issue #15) when the right one is absent, drops any bot fields the LLM included, and validates each item for precise Norwegian error paths (`«[1].venue.name»`).
  - It **ignores any submitted offset and recomputes it** with `_stamp`/`_end_stamp`, because all times are Oslo local time. Then it sets `id`/`series`/metadata and runs `validate_event`.
  - `from-issue` routes a form that has a «JSON» heading here.
- `join_existing_series!(events, root)` (`src/issue.jl`), run by `from-issue` on every new submission (form, table, JSON): a group of new events (by own series, or id without date) joins the latest existing series with the same series id or `_slug`ged title **and** the same organiser or venue name (`_same_host`); joined events get that `series` and id `<series>-YYYY-MM-DD`, and the bot report names the series. A date already in the series then collides by path and is refused; so does one under another id with the same start (`series_starts`, `_start_key`: series + start to the minute).
- `src/table.jl`: the spreadsheet route (issue form `nytt-arrangement-tabell.yml`, label «Tabell»).
  - `parse_table` reads pasted cells: tab-separated is the normal case; `;`/`,` CSV and quoted cells are also accepted.
  - `events_from_table`: row 1 holds the column headings (`TABLE_COLUMNS`, the form's labels, any order, with aliases), row 2 the defaults, and later rows only the deviations (blank = default, `-` clears, «Avlyst» in Status).
  - Each row becomes a form dict and goes through `events_from_form`, so the rules and messages stay identical. Errors carry the spreadsheet row number (row 1 = headings). Rows with the same title share a `series`.
  - `table_template_csv()` is the downloadable `mal/arrangementer-mal.csv` (semicolon-separated, with a UTF-8 BOM for Norwegian Excel). A test checks that it converts cleanly.
  - `_date` (in `issue.jl`) also accepts `DD.MM.ÅÅÅÅ`, which is how Norwegian Excel copies dates.

### Event data contract

`schema/tango-event.schema.json` (draft-07, `additionalProperties: false`) is the source of truth for the event format. When you add a field, update the schema, the renderer, the issue forms (`src/issue.jl`, `src/correction.jl`) and the submission schema/rules (`src/submission.jl`, `src/llms.jl`) together. Files live at `events/YYYY/MM-englishmonth/YYYY-MM-DD-<id>.json`. **Every event is dated** (`start` is required). Repeating events (weekly milongas, courses) are one file per date sharing a `series` id, because weekly events get cancelled and their details (DJ, price) vary from date to date. Cancelled dates use `status: "cancelled"` rather than being deleted. `types` is a list with one or more of `TYPE_ORDER` (`src/labels.jl`): a class followed by a milonga is `["class","milonga"]` and an open-air milonga is `["milonga","outdoor"]` («Utetango»). There are no combined types. The renderer shows one chip per type (`_type_chips`), `data-type` holds all of them separated by spaces, and the type filter matches an event that has any of the ticked types. The forms use checkboxes; the spreadsheet takes a comma list («Kurs, Milonga»), and «Kurs og milonga» also works. `events_from_json` converts an assistant's singular `type` field. `pay_what_you_can: true` marks a pay-what-you-can entry (shown as «Betal det du kan» / «Pay what you can» / «A la gorra»; `price_nok` is then a suggested amount); it is left out otherwise. It is its own control in every route: the checkbox «Betal det du kan» in the new-event form (`_ticked`; «Pris (kr)» is then the suggestion and may be empty, otherwise a whole number), a column of the same name in the spreadsheet («Ja»), a dropdown «Som før / Ja – betal det du kan / Nei – fast pris» in the correction form (a number in «Pris» changes only the amount there), and a Ja/Nei `:choice` field `pay_what_you_can` in the editor form. The old wording in «Pris (kr)» («betal det du kan, 100», `_parse_price`, `PWYC_PHRASES` in three languages) still sets it everywhere, for old issues and spreadsheets. `_set_pwyc` inserts the key in its schema place. `venue` is an object `{name, address, city}`; `link` is the official event page, while `source`/`source_url` record where the data came from.

- `start` is either an ISO datetime with an offset (`2026-10-01T19:00:00+02:00`) or a bare date (`2026-10-02`). `_date_label` tries the datetime form first and falls back to the date form. The schema requires seconds in datetimes because `_date_label` parses `HH:MM:SS`.
- **No shouting or creative capitals** (`_caps_problem`, `_word_ok`, `CAPS_FIELDS` in issue.jl): titles (any language) may have at most half their letters as capitals (from 6 letters) and only ordinary word shapes: lower case, capitalised or capitalised parts of ≥3 letters joined («TangoAkutten», «OnsdagsPractica»), or abbreviations of 1–4 capitals (+ ≤2 lower case: «ESA», «DJs»); descriptions only the 50% rule (from 20 letters, ignoring links, @handles, #tags). The same title rule covers organiser, venue name and address (`kind=:title`); DJ and teachers get only the 50% rule (`kind=:name`), since names like «DiStefano» have inner capitals (`CAPS_FIELDS` maps form labels to kinds). When a text has no lower case at all, the suggestion capitalises every word, no guessing (small words like «de», «og» lower case after the first). Messages: «korte ord som ESA er greit» (ESA is an exclamation, allowed for being short, not an abbreviation; DJ isn't mentioned since it has its own field); names get no such tail. Checked in the form/spreadsheet, JSON (`[n] «title»`), corrections (changed fields only) and `set_field` (editors); stored events aren't validated against it. The message suggests a spelling. Calibrated on the Oslo titles (only «NOCHE LOCA!» failed, since fixed).
- **DJ without a «DJ»/«TDJ» prefix** (`_strip_dj_prefix`, issue.jl): «TDJ Ana», «Tdj: Ana», «DJ-Ana» → «Ana» (a standalone prefix word only, «Djordje» stays) in the form/spreadsheet, JSON, corrections and `set_field`; the capitals check sees the stripped name. Nothing is refused: the parsers add a line to `notes` (`events_from_form/table/json`, `apply_correction` take `notes=`), and `from-issue` shows them as «Merk:» in the bot's report (`_notes_md`). The AI rules say so too.
- **Titles never carry the organiser** («Nybegynnerkurs i tango», not «… (Tango Puente)»), unless the organiser's name is the event's own name («Otra Milonga», «Kristiania Tango Festival»). The schema's `title` description, `llm_rules` and the form/spreadsheet help say so. The list row shows the organiser instead, as its first fact (`_row_org`, html.jl), unless it is already in the title (any language) or is the DJ or a teacher. Week cells (`_cell`) leave it out for space.
- The JS **"Faste aktiviteter"** filter matches rows with a non-empty `data-series`.
- Cancelled events render with class `cancelled` and an "Avlyst" chip, and stay visible on the page.
- `data-type`, `data-date`, `data-end`, `data-series`, `data-search` and `data-music` attributes on each `<article class="event">` are the interface between the Julia output and the inline JS. `data-end` comes from `_end_day`: the last day the event runs, using the same «ends by 06:00 = previous evening» rule as `_date_label`.
- The time filter defaults to **Kommende**: events whose end day is today or later, so ongoing festivals still show. **The views carry only events that haven't ended by the build date**: `render_events_html(…; from=today)` (passed by `write_site` and `build`) drops older events, and in the list/map rows the days of a multi-day event that are already over; the week view keeps the whole current week. So no old events show without JavaScript, and the pages don't grow with the archive. The script still hides events that end between nightly builds. Without `from` (the default) every event given is rendered, which the tests rely on.
- **Past events** are on the archive pages (`render_archive_html(events, year)`, `view="archive"`): `tidligere-YYYY.html` per year (`archive_file`, by end day; newest day first via `_compact_view(…; rev=true)`; search and type/music filters, no time/sort; year links), and `tidligere.html` (`ARCHIVE_PAGE`) = the newest year, canonical to its year page. The views link there from the footer only («Tidligere arrangementer»; it is not core, so not in the summary line). There is no «Alle» time option any more; an old `?when=all` link is sent to the archive by the page script (`data-archive` on `#when`, `location.replace`, keeping `q`/`type`/`music`). `test/js/filters.js` reports that as `{replaced}`; browser tests that depend on the date fix the clock with `freeze_date(page, day)`.
- `test/js/filters.js` runs the page's real inline script in Node against a fixed date with a minimal DOM stand-in. The `upcoming filter` testset uses it when `node` is on the PATH (it is on GitHub runners) and skips otherwise.

### Gotchas

- The JS lives inside a Julia `"""` string, so a JS template literal `${...}` must be written `\${...}`. Otherwise Julia tries to interpolate it.
- The tests assert that the rendered output never contains the string `nothing`, so route optional fields through `_val`/`_esc`.
- `public/index.html` is generated output.
- JSONSchema.jl reports only the first issue per event. `_issue_message` in `src/validate.jl` turns it into a short message, and lists the key names for unknown-key errors.
- `series_start_warnings` (validate, build, site) **warns** about two events of one series with the same start but doesn't fail: same day at other times is normal for festivals (the Kristiania festival series has afternoon and evening milongas), so don't tighten it to whole days.
- Video ids are re-checked with regexes in `_video` and URLs must be `http(s)` (`_http`) before they are embedded, independently of the schema. Keep both checks.

## Repos and GitHub workflows

This is the code repo, `github.com/Tangokalender/TangoKalender.jl` (package `TangoKalender`; registered nowhere, installed by URL). The data lives in one repo per city: Oslo is `Tangokalender/tangokalender.github.io`, the organisation's root Pages site, served at https://tango.oslo.no/ (custom domain since 2026-10-12; `tangokalender.github.io/…` redirects there, and so would any other repo of the org without its own domain, so a new city needs one; see docs/src/maintainers/new-city.md). A data repo has `site.toml`, `events/`, `venues.json`, `assets/og-image.png`, the rendered issue forms and a `Project.toml` pinning this package (`[sources]` url + rev); start one with `tangokalender init-site`. Releases: bump `version` in `Project.toml`, tag `vX.Y.Z`, and move the `v1` tag that data repos' workflows may follow. No site URL may be hard-coded here (the «site URL drift» test).

- **Reusable workflows for the city data repos** (`on: workflow_call`): `site-validate.yml`, `site-pages.yml` (build + deploy to Pages; the caller grants `pages: write`/`id-token: write`) and `site-intake.yml` (inputs `new-label`, `fix-label`, `needs-fix-label`). They run `julia --project=. -m TangoKalender …` in the caller's checkout, so a data repo's `Project.toml` (TangoKalender pinned via `[sources]` url + rev) decides the code version. A data repo calls `Tangokalender/TangoKalender.jl/.github/workflows/site-*.yml@v1`. The steps below describe them.
- `ci.yml`: tests on the latest Julia release (`'1'`; the compat floor is 1.12, which Pkg apps need), on PRs and on `main`. `tangoedit.yml`: the trimmed build, monthly and on demand.
- `site-pages.yml`: runs `site events _site`, which writes `index.html` (the compact list), `uke.html`, `kart.html`, `kort.html` (upcoming only), `tidligere.html` + `tidligere-YYYY.html` (past events), `arrangement/<id>/` plus `.ics`, `kalender.ics`, `rss.xml`, `legg-til.html` (plus the `for-ki.html` redirect and `mal/arrangementer-mal.csv`), `llms.txt` and both schemas under `schema/`, served at their `$id`s, e.g. `https://tango.oslo.no/schema/tango-event.schema.json` (`_site_schema` rewrites the package copies' `$id`, which keep the old github.io address as the canonical id, to the site's URL). It deploys to GitHub Pages on `main` changes and nightly. `public/` and `_site/` are gitignored.
- `site-intake.yml`: issue opened or edited with the label `nytt-arrangement` or `rettelse` → `from-issue` → `peter-evans/create-pull-request` on branch `arrangement/issue-<n>`, then a comment on the issue with the report. `from-issue --outputs=$GITHUB_OUTPUT` emits a one-line `pr_title` and `issue_title`, which name the PR and rename the issue. `add-paths: events` must stay a directory, so that moved files are committed as deletions too. Failures get the `trenger-retting` label.
  - «Move changes onto the latest main» stashes `events`/`venues.json`, fetches `main` and pops them back before the PR step. Without it, a workflow change merged to `main` during the run (e.g. Dependabot) left the PR branch on the old `main`, and GitHub refused the push (issue #13). When the pop conflicts (another submission for the same event was merged during the run; Oslo #41/#42), it resets to the new `main`, drops the stash and runs `from-issue` (and `geocode`) again there. The comment step says «⚠️ … ingen pull request» and adds `trenger-retting` whenever the form was read but the PR step didn't succeed (`steps.pr.outcome`), never «✅ Takk». Tested by simulating the step's script against a local origin with a stub `julia`/`gh`. A re-run of a failed intake run reuses the old commit; edit the issue instead to start a fresh run.
  - **Security:** the issue body and title are untrusted. Only pass them through `env:` or action inputs, never with `${{ }}` inside `run:`.
  - Bot PRs made with `GITHUB_TOKEN` don't trigger `ci.yml`. That's why `from-issue` validates the whole tree itself.
  - Lint with `actionlint` (and `shellcheck`) after editing workflows.
- Tests that depend on today's date must pin it: `events_from_form(...; today=)` or `from-issue --today=`. The fixtures in `test/fixtures/issues/` have fixed 2026 dates.

## Related design notes

`/workspace/design_notes.md` describes a planned "v2.0" pipeline: GitHub Issue Form → Action writes one JSON file per event under `events/` → a Julia build → GitHub Pages. The file layout, the extra fields, the issue form and the workflows have been adopted (the intake opens a PR instead of committing directly, and the Julia parser replaces the design doc's injection-prone github-script). Its Mustache/JSON3 build script has not. Its `start_date`/`notes`/`platform_youtube` shapes were deliberately mapped to `start`/`description`/`video.platform`.
